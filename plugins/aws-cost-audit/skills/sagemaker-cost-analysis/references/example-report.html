How this works

method · coverage · caveats

Where the SageMaker spend goes

Dollars are exact. Every figure is a share of the amount AWS actually billed, distributed across the spaces active on that day pro-rata by observed runtime. Daily and period totals therefore reconcile to the bill by construction; no cost is ever computed as hours × rate.

A day's billed hours are partitioned, not estimated. Each instance type's billed hours for a day are divided among the spaces active that day: CloudTrail supplies the type directly where it reaches, and whatever is left is rank-matched (the space with the most remaining hours draws from the type with the most remaining hours). A space is not assumed to sit on one instance type all day — apps get recreated on bigger instances mid-afternoon. Every row records its basis in the Source column.

How the attribution works, and why it reconciles

Cost Explorer stops at SERVICE and USAGE_TYPE: it knows what SageMaker cost, not whose work spent it. Two independent sources reconstruct the layer below, and the bill stays the arbiter of the total.

Two numbers, kept apart

Priced coverage: 99.7% of billed runtime hours (255.0h of 255.8h). A shortfall here is real spend with no observed space activity at all — it is listed in the reconciliation table and excluded from space and file rows rather than spread around. The target is 98%.

The method's error bar is observed runtime against billed runtime: 102.6% (262.4h observed against 255.8h billed). Slightly above 100% is expected and benign — billing starts when an app reaches InService while CreateApp fires a minute or two earlier, and each occupancy cluster counts its trailing 5-minute bin whole. It has not been tuned to reach 100%. Above about 112%, something is double-counted.

Splitting a space-day across notebooks

Per-file cost is an allocation, not a measurement. Studio logs a jl-cell-executed event for every cell run, so this run knows about 8,215 real cell executions across 60 notebooks — that a notebook ran, not merely that it was open. Each event names its notebook only as an MD5 of the file path; 99.5% of executions were matched back to a real path, and the 2 that were not appear as unidentified rows keeping their cost rather than being dropped. Weighting on this run: 70% by executions × that notebook's own sec/cell; 23% by executions × the corpus median sec/cell; 7% by editor open/sync events only. Seconds-per-cell comes from each notebook's own saved execution metadata (corpus median 9.8 s). That metadata records only each cell's most recent run, so it is a profile of the notebook rather than a measurement of any one day — a notebook whose runtime changed mid-period is priced with its latest profile throughout. Treat the file ranking as reliable and any single figure as an estimate. On this run 7% of the $2,475.33 allocated to files ($180.82) rests on a split flagged wide error — too few logged events that day, or events spread so evenly across the open files that the ratio is indistinguishable from dividing the day equally. Those rows rank; they do not measure.

Sources, gaps and warnings

Sources: CloudTrail CreateApp/DeleteApp from 2026-06-22 (Event history reaches no further back) — exact spans and exact instance type; CloudWatch Logs Insights occupancy over 5 app log streams — full history, instance type inferred.

Gap: no CloudTrail trail or event data store exists, so exact spans stop at the Event-history horizon. Everything older is reconstructed from log occupancy, which cannot observe the instance type directly — those rows carry type:rank-match rather than type:cloudtrail in the Source column.

Unvalidated usage families present: Notebook. Their attribution strategy has not been reconciled against a bill; treat their rows as indicative.

Unattributed: $0.05 of runtime cost had no space activity in any source. It is real spend the reconstruction cannot place; it appears in the reconciliation table and is excluded from space and file rows.
